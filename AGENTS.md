# Tasmota Irrigation

## Порядок работы над задачей

Задача сформулирована как алгоритм («перенеси», «вынеси», «сделай так») — сначала
выведи из целей ([`docs/vision.md`](docs/vision.md)) требование и ограничение, и
проговори их до кода. Не выводится однозначно — спроси.

**Если вывод ничего не меняет — не пиши его.** Не применяй к шагам внутри
согласова��ного плана: там цель уже выведена.

Процедура: скилл `requirements-first`.

Система полива: `watering.be` — Berry-скрипт (FSM) для Tasmota. Локальная разработка и тесты вместо реального железа.

Перед любой работой прочитай:
- `BERRY_TASMOTA_CONTEXT.md` — ключевые факты, gotchas (Berry), архитектура, текущее состояние полей.
- `tests.md` — карта тестовых кейсов, как их собирать и гонять.

Главные правила:
- Источник правды — git, а не один файл. `watering.be` был единым источником правды
  до разбиения на модули; теперь правда в **семи обычных исходниках** в корне
  репозитория, и они редактируются напрямую: генератора кода и артефакта сборки нет.
  Тесты фиксируют поведение, а не диктуют.
- Пуш на устройство — **7 файлов** через `make deploy`: 6 модулей первыми, затем
  `watering.be`. Порядок задан кортежем `MODULE_FILES` в `deploy.py`. Запускать:
  `.pyvenv/bin/python deploy.py` (в venv есть `requests` и `diff_match_patch`).
  `rc=0` — устройство обновлено и скрипт загрузился; при любой проблеме `rc=1`.
  Единственная точка входа на устройстве не изменилась: `autoexec.be` по-прежнему
  делает `load("watering.be")`, и это же имя остаётся целью hot-reload в `deploy.py`.
- После деплоя всегда гонять `.pyvenv/bin/python check_device.py` — отдельный
  сценарий, **только чтение**: лог без крашей, `/` 200, `/?m=1` отрисовывает
  `Канал 1`, `GET /svc` → 200 «Сервисный режим» (таймаут = провал), `Status 10`
  содержит блок `Watering`. `rc=0` = устройство живо и раздаёт веб.
  Разделение намеренное: сетевой флек не должен портить `rc` деплоя, и проверки
  можно повторять сколько угодно, без заливки. Холодный старт (гонка «WiFi
  против фазы 2», `/svc` при `BrRestart`) — `check_device.py --cold-restart`:
  шлёт `Restart 1`, ждёт возврата и проверяет уже так.
- Заливка при провале любого файла **не** доводит дело до рестарта: устройство с
  половиной набора файлов нельзя чинить рестартом. `deploy.py` сам решает и печатает,
  какой файл не залился.
- После деплоя на реальное железо выполнить ручной чеклист из `tests.md` → «Проверка на реальном железе» (кнопки Tools/Configuration, каналы на главной, раскрытие секций, тултип иконки) — сначала `.pyvenv/bin/python check_device.py`.
- Если после `BrRestart` скрипт не загрузился (`MEMORY ALLOCATION FAILED`, каналы пропали) — полный рестарт устройства `cmnd=Restart 1`, не только VM. deploy.py сам следит за этим: читает `/in` (frag%) перед аплоадом и при `frag >= 40%` (или `MEMORY ALLOCATION FAILED` после BrRestart) делает полный `Restart 1`.
- Не трогать недоделанные калибровки %/мВ (`Raw2Hymidity`/`Hymidity2Raw`/`Raw2mV`/`mV2Raw`/`Raw2Hu`) и EMA-режим без явного запроса.
- Тесты только через `python3 tests/run_all.py` (или `python3 tests/build.py tests/cases/<case>.be`); всегда зелёные.
- Побайтовые снимки вывода — обязательный гейт любого рефакторинга UI:
  `python3 tests/golden.py` (`rc=0`). Существующие HTML-тесты ищут подстроки, поэтому
  пропущенная скобка или выпавшая ветка оставили бы их зелёными; снимок — нет.
- Если `python3 tests/run_all.py` не находит berry — развернуть среду: `bash tests/setup_berry.sh` (бинарь: `~/.local/bin/berry`; версия зафиксирована в скрипте).

## Карта модулей

«В каком файле искать X» — здесь. Все семь лежат в корне ФС устройства.

| Файл | Что внутри | Кто импортирует |
|---|---|---|
| `cfg.be` | `MAX_CHANNELS`, `BOOT_INIT_DELAY_MS` | `watering.be`, `web.be` |
| `web_kit.be` | `wrow`, `wgrp`, `wonclick`, `wtoggle`, `wpill` | `sensors.be`, `fsm.be`, `web.be` |
| `sensors.be` | `EMA`, `AbstractSensor`, `SoilSensor`, `FlowSensor` (презентация `web_sensor` остаётся здесь — ADR-6) | `watering.be`, `fsm.be` |
| `store.be` | `PersistStore` — **единственный** импортёр `persist` во всём проекте | `watering.be`, `fsm.be` |
| `fsm.be` | `FloodPreset`, `Plant` | `watering.be` |
| `web.be` | `class Web`: главная страница, `/svc` + 12 хелперов, `_TimeStr`. Держит `var d` — ссылку на драйвера, внедрённую в `init(d)` | `watering.be` |
| `watering.be` | импорты, `class Watering` (диспетчер, `init`, телеметрия, 4 делегата → `self.ui.*`), бут-эпилог | — это точка входа |

Правило границ: единственное обратное ребро — `web → драйвер` через `self.d` (duck-typed,
`web.be` не импортирует ни `sensors`, ни `store`, ни `fsm`). Всё остальное — DAG в одну
сторону. Порядок `import` в шапке неважен: проверено перестановкой, прогоны зелёные.

У каждого модуля в конце файла стоит блок явной публикации (`cfg.MAX_CHANNELS = MAX_CHANNELS`
и т.п.): Berry `module()` **не** собирает имена файла автоматически, без этого
`cfg.MAX_CHANNELS` даёт `attribute_error`.
