# Тесты watering.be

Характеризационные тесты логики полива. Запускаются на **локальном интерпретаторе Berry** (без железа), Tasmota-API эмулируется стабом. Цель — зафиксировать текущее поведение (`rule_power`, `auto_flood`, таймеры) до будущего рефакторинга: если после правок тесты станут красными — поведение изменилось.

Актуальный набор покрывает **итерацию 2 (многоканальность)**: `Watering`-диспетчер + `Plant` на канал (свой насос `Power{Num}`, per-channel persist `P{Num}_*`, сериализация общего счётчика C1) и **сервисный режим** (`/svc`, калибровка датчика потока). Сводка на текущий момент: **796 PASS / 0 FAIL** (кейсы 00–44).

## Как запустить

```sh
bash tests/setup_berry.sh                 # развернуть Berry VM с зафиксированной версией (один раз)
python3 tests/run_all.py                  # все тесты (бинарь ищется в PATH, ~/.local/bin, $BERRY_BIN)
python3 tests/run_all.py /path/to/berry   # указать бинарник berry явно
python3 tests/build.py tests/cases/10_rule_power_on.be  # один тест
```

Требуется собранный бинарник Berry (см. ниже). Никаких зависимостей Python — только файлы в `tests/`.

## Развёртывание (процедура с зафиксированными версиями)

Бинарь Berry **не живёт в `/tmp`** (теряется при каждом ребуте) и **не кэшируется** где-то ещё. Среда разворачивается скриптом `tests/setup_berry.sh`, который сам клонирует и собирает **пиннённую версию**:

| Зависимость | Версия | Где зафиксировано |
|-------------|--------|-------------------|
| Berry VM | `v1.1.0` (тег, коммит `b5ede66`) + локальный патч `tests/patches/berry-1.1.0-gc-stack-init.patch` | `tests/setup_berry.sh` (`BERRY_REF`, патч применяется автоматически) |
| Сборка | Makefile репо + `gcc` + `libreadline` (cmake НЕ нужен для v1.1.0) | `tests/setup_berry.sh` |
| Python | `>= 3.10` | `tests/build.py`, `tests/run_all.py` |

**Зачем патч:** в чистом v1.1.0 после `stack_resize` новые слоты VM-стека остаются
мусорными, `precall` может захватить их `vm->top`'ом до записи, а GC
(`premark_stack` → `mark_gray_var`) сканирует диапазон `[stack, top)` целиком —
при определённой раскладке памяти это nondeterministic SIGSEGV (воспроизводилось
на тесте `91_golden_service` при запуске с абсолютным путём; апстрим и в master
не починил). Патч nil-заполняет новый хвост стека в `stack_resize` и начальный
стек в `be_vm_new`. Проверяется valgrind: до патча — отчёт GC на неинициализированном
слоте, после — только старый парсерский шум `be_eqstr` (есть и на HEAD, без падений).

```
bash tests/setup_berry.sh
# -> исходники:  ~/.local/src/berry
# -> бинарь:     ~/.local/bin/berry
```

Тестеры (`run_all.py`/`build.py`) ищут бинарь в порядке: **аргумент командной строки > `$BERRY_BIN` > `PATH` > `~/.local/bin/berry`**. Настрой `PATH` (например `export PATH="$HOME/.local/bin:$PATH"` в `~/.bashrc`).

### Важно о stock Berry vs Tasmota-патч

Это **stock Berry 1.1.0**, а не Tasmota-сборка. Реальные отличия, зафиксированные тестами:

- `introspect.setmodule()` в stock **отсутствует**; persist подменяется файлом-модулем `tests/modules/persist.be` (класс-инстанс, как реальный persist).
- `string.format('%d', '1')` (строка) в stock даёт **пусто**, в Tasmota-патче — `'1'`. Поэтому `FlowSensor.Reset()` использует `%s`, а не `%d` (watering.be:253).
- `string.format('%i'/…` поведение идентично Tasmota по остальным тестам.

## Структура

| Путь | Что это |
|------|---------|
| `tests/harness_header.be` | Преамбула: фреймворк ассертов + стабы Tasmota. Вклеивается в начало каждого теста |

| `tests/cases/NN_*.be` | Тест-кейсы |
| `tests/build.py` | Склейка: `header + watering.be + case` → `tests/out/combined.be`, запуск berry |
| `tests/run_all.py` | Прогон всех кейсов и сводка |
| `tests/golden.py` | Побайтовое сравнение вывода golden-кейсов с эталоном `tests/golden/*.out` |
| `tests/cases/9*_golden_*.be` | Golden-кейсы: снимки полного вывода `web_sensor()` и `page_service()` |
| `tests/golden/*.out` | Эталонные снимки (в гит входят) |
| `tests/out/` | Сгенерировано, в гит не входит |

`build.py` копирует в `tests/out/` **и стабы из `tests/modules/`, и корневые `*.be`**
(кроме `autoexec.be` и самого `watering.be`, он склеивается текстом). Благодаря этому
`import <модуль>` в тестах резолвится ровно так же, как на устройстве, — ошибка в
импортах всплывает в локальном прогоне, а не после заливки.

### Golden-снимки

Остальные HTML-кейсы проверяют вывод через `string.find(...) >= 0`, то есть ищут
подстроки. Этого недостаточно: пропущенная скобка, лишний `</td>` или выпавшая ветка
оставили бы их зелёными. Golden-кейсы печатают полный вывод целиком, `golden.py`
сравнивает его **побайтово** с эталоном и печатает unified diff при расхождении.

```bash
python3 tests/golden.py                    # оба снимка, rc=0 при совпадении
python3 tests/golden.py 90_golden_web.be   # один кейс
```

Эталон в гит входит; пересоздаётся сам, только если файла ещё нет. Снимок попутно
фиксирует и собственные `print` драйвера (порядок инициализации) — это часть
наблюдаемого поведения, поэтому он там есть намеренно.

Снимок — гейт контракта «вывод не изменился». Правка UI, которая меняет байты в
`tests/golden/*.out`, — это изменение поведения, а не рефакторинг.

## Как писать тест-кейс

Кейс — это дробный Berry-скрипт, который исполняется **после** загрузки `watering.be`. В нём доступны:

### Ассерты (из header)

```berry
assert_true(boolean_value, "описание")        # положить boolean
assert_eq(actual, expected, "описание")       # сравнить значения (str-эквивалентно)
section("имя_секции")                          # разделитель вывода
```

При провале выводится `FAIL:` и считается счётчик; в конце каждого кейса не требуется итог — `run_all.py` считает `PASS:`/`FAIL:` сам.

### Управление симулятором

Глобальный объект `SIM` — модель Tasmota:

```berry
SIM['millis'] = 5000        # внутренние часы tasmota.millis()
SIM['sensors'] = {'ANALOG': {'A1': 900, 'A2': 900}, 'COUNTER': {'C1': 0, 'C2': 0}}
SIM['cmds']                 # список всех tasmota.cmd(...) — команды, отправленные в Tasmota
SIM['timers']               # map: id -> {'delay': ms, 'cb': callback}  (set_timer записывает)
SIM['rules']                # map: триггер -> callback (add_rule)
SIM['websend']              # собранные web_send_decimal()
SIM['append']               # собранные response_append()
```

Датчики в объекты `wp1.SoilSensors[0]` попадают при `Update()`, а не при прямой правке `/sensors`:

```berry
SIM['sensors']['ANALOG']['A1'] = 900
wp1.SoilSensors[0].Update(json.load(tasmota.read_sensors()))
```

Хелперы:

```berry
cmds_include("Power1 1")    # была ли в истории команд подстрока
```

### Основной объект

`wp1` — глобальное Water из boot-секции `watering.be` (создался при сборке). Вызывайте его методы напрямую:

```berry
wp1.rule_power({'State': 1}, 'POWER1')            # событие реле канала 1 (диспетчер по PowerMap)
wp1.auto_flood()                                  # sweep-планировщик (round-robin по каналам)
wp1.every_second()
wp1.pulseencode(60)                               # чистая функция
```

### Доступ к каналам (`wp1.plants[i]`) — ВАЖНО (баг Berry 1.1.0)

`wp1.plants` — список каналов (`Plant`): `wp1.plants[0]`, `wp1.plants[1]`, …

**Не пишите цепочки `wp1.plants[0].X` в top-level коде теста** — на stock Berry 1.1.0
(global → member-список → индекс → member) это падает `index_error: list index out of range`
после накопления мусора/персист-записей (зафиксировано в тестах 32/33). Обязательно хойстите
в локальную переменную и переобъявляйте её после пересоздания `wp1`:

```berry
var P1 = wp1.plants[0]        # локальная ссылка на канал 1
P1.SoilMaxHymidity = nil      # OK
assert_eq(P1.Preset.Type, 'dry', "...")

wp1 = Watering()              # пересоздание (reboot) — обновите и ссылку:
var P1 = wp1.plants[0]
```

Внутри методов классов (`self.plants[0].X`) баг не проявляется; безопасны и `wp1.Store.method(...)`,
и `wp1.SoilSensors[0].Update(...)` (цепочка global → member → **индекс → метод-вызов**).
А вот атрибут ПОСЛЕ индекса (`wp1.FlowSensors[0].Scale`, `wp1.plants[1].WaterIsOn()` не является —
это метод) ломается так же: **койстите и члены-списки канала/сенсоров** (`var F0 = wp1.FlowSensors[0]`,
`var P2 = wp1.plants[1]`), см. `41_service_mode.be`.

Таймеры не «тикают» сами — их зарегистрированные колбэки в `SIM['timers']` можно вызывать вручную или проверять по `id`. Имена таймеров каналов — `ID_SOILTRANSITION_AFTERFLOOD_P{Num}` (счётчик единый).

### Пример кейса

```berry
import json

section("заливка_начинается")

SIM['sensors']['ANALOG']['A1'] = 900     # сухой грунт
SIM['millis'] = 1000
wp1.rule_power({'State': 1}, 'POWER1')

assert_eq(wp1.Power1, 1, "реле вкл")
assert_true(wp1.FinishRule != nil, "сработало правило окончания")
assert_true(cmds_include("TelePeriod 10"), "быстрая телеметрия во время помпы")
```

## Тонкости Berry (о чём легко споткнуться)

- `true`/`false` — **строчными** literal'ом (не слова `True`/`False`).
- Длина строки: `size(s)` (в байтах); `string.len()` нет.
- Подстроки: `string.find(hay, needle)` возвращает индекс или `-1`; `string.split(s, sep)` и `string.replace` работают; `string.mid` нет.
- map-объекты не переприсваивают члены через `=`; для переопределения стаб использует module-инстанции (см. `webserver`).
- Errors: `try ... except .. as e, m ... end`.
- `list.push(x)` — добавить элемент; `list.size()` — длина.
- JSON: `json.load(str)`, `json.dump(map)`.

## Проверка на реальном железе

Локальные тесты не покрывают деплой и работу Berry-рантайма на устройстве. Каждый релиз проверяй на железе.

### Автоматическая (deploy.py + check_device.py)

```sh
.pyvenv/bin/python deploy.py        # upload + verify + BrRestart + проверки; rc=0 = устройство обновлено, скрипт загрузился
.pyvenv/bin/python check_device.py  # постдеплой-смоук, только чтение; rc=0 = устройство живо, /svc отвечает
.pyvenv/bin/python check_device.py --cold-restart   # Restart 1 + проверка холодного старта
```

Два сценария разделены намеренно: деплой **пишет** на устройство и его `rc=0`
означает «заливка верифицирована и скрипт поднялся», `check_device.py` только
**читает** состояние. Так сетевой флек не превращает успешную заливку в
«деплой упал» (такое уже было: таймаут чтения лога давал `rc=1` при живом
деплое), и проверки можно гонять сколько угодно — после деплоя, после ручного
`Restart 1`, после любых правок на железе. `deploy.py` при успехе сам печатает
подсказку про следующий шаг.

`deploy.py` делает сам и падает (rc=1) при любой проблеме:

- заливает 7 файлов из кортежа `MODULE_FILES` (`deploy.py`): 6 модулей первыми, `watering.be` последним, каждый — только если изменился; верифицирует загрузку (`/ufsd?download=...` 200);
- если заливка или верификация хоть одного файла не прошла — **рестарт не делает** и печатает, какой файл не залился: устройство с неполным набором файлов рестартом не чинится, а ломается;
- перед аплоадом читает `/in` (heap: `Free Memory ... (frag. N%)`): при `frag >= 40%` делает полный рестарт устройства (`Restart 1`) и ждёт его возврата — фрагментированный heap ломает и `/ufsu`-аплоад, и загрузку скрипта;
- `BrRestart` и ждёт в логе маркер `Watering driver initialized`;
- собирает лог после старта и ищет краши/ошибки инициализации (`type_error`, `syntax_error`, `index_error`, `stack traceback`, `undeclared`, `MEMORY ALLOCATION FAILED`, `Giving up on delayed sensor init`, `ERROR: Watering driver NOT registered`);
- если после `BrRestart` в логе `MEMORY ALLOCATION FAILED` — автоматически повторяет с полным `Restart 1` (очищает heap и лог);
- `GET /` — страница 200 и в HTML есть секции каналов (`tr.sec`);
- сетевые таймауты помечаются отдельной проблемой + пинг до устройства (одна проверка за прогон).

Если `BrRestart` после деплоя дал `MEMORY ALLOCATION FAILED` и каналы не отдаются — сделай полный рестарт устройства (`cmnd=Restart 1`), не только VM.

`check_device.py` делает сам и падает (rc=1) при любой проблеме:

- читает лог и ищет краши-паттерны (те же, что деплой). Маркер
  `Watering driver initialized` в обычном режиме — только с пометкой, не
  ошибка: RAM-лог — кольцевой буфер короче аптайма, и на живом устройстве
  строки старта уже вытеснены. Жёстко маркер требует `--cold-restart`
  (там `collect_log` ждёт его после `Restart 1`);
- `GET /` — 200 и `tr.sec` (та же проверка, что в деплое);
- `GET /?m=1` — 200 и `Канал 1`: строки каналов рендерятся именно этим XHR'ом,
  тогда как `tr.sec` на статической `/` есть даже в CSS-инжекте (см. ограничение 3);
- `GET /svc` — 200 и «Сервисный режим». **Таймаут здесь = провал**: висящий
  маршрут — это и есть исторический баг (см. ограничение 2), запрос не
  дожидается ответа и падает с `Timeout`;
- `GET /cm?cmnd=Status 10` (`StatusSNS`) — есть блок `"Watering"`: доказывает,
  что `json_append()` драйвера жив и телеметрия идёт;
- `--cold-restart` — шлёт `Restart 1`, ждёт возврата устройства
  (`wait_device_up`), затем те же проверки с ожиданием маркера: это путь,
  который проверяет холодный старт, то есть гонку «WiFi против фазы 2»;
- ответы декодируются в UTF-8 принудительно: Tasmota отдаёт `text/html` без
  charset, иначе `r.text` даёт мусор вместо кириллицы и маркеры соврут;
- все проверки прогоняются до решения об exit-коде (полная картина, как в деплое).

### Ручной чеклист

1. Кнопки **Tools** и **Configuration** на главной присутствуют (инжекция `web_add_main_button` работает).
2. На главной видны все каналы (секции `Канал 1..N` + `Common`).
3. Клик по секции раскрывает её (подгружаются детали: датчик, сессии, кнопки уставок).
4. Статус-иконка (💧/⏳/💦) показывает тултип-легенду по клику, страница не сворачивается/не прыгает (stopPropagation).
5. В консоли устройства (`/cs?c2=0`) после старта нет `type_error`/`stack traceback`/`NOT registered`.
6. Сервисный режим: `/svc` → «Включить сервисный режим»/«Выйти» работают (открытие страницы само ничего не переключает). Маршрут живёт сразу после любого рестарта (`BrRestart` и полного `Restart 1`) — это проверяется автоматически: `check_device.py` требует `GET /svc` → 200 «Сервисный режим», а таймаут этого запроса считается провалом; ручной обход (полный `Restart 1` или `web_add_handler()` из berry-консоли) больше не нужен. История вопроса — «Известные ограничения деплоя» п. 2. В активном режиме на главной (`?m=1`) — баннер «Сервисный режим: включен»; кнопки ON/OFF каналов включают/выключают реле, второй канал при занятом первом отклоняется; во время прокачки страница `/svc` сама обновляется каждые ~2 с и показывает живой расход (ml/min по текущей калибровке) в fieldset «Прогон» — удобно для регулировки форсунок; после OFF в «Последний прогон» видны средний расход за прокачку и время окончания — удобно для сверки с замером объёма; калибровка (прогон канала → измерить объём → `vol`) обновляет scale, ручное `scale`-поле применяется; автополив во время режима не стартует; выход из режима стопает идущий сервисный прогон.
7. Единицы (мл): в detail канала на главной ряд «LastFloodVol (мл)» и поля попапа «Soak start dose (ml)»/«Max flood (ml)»/«Flood dose default (ml)» показывают значения в мл; изменение Max flood/дозы в попапе применяется сразу (эскалация полива капом новой Max flood) и переживает ребут; backflow редактируется только командой Store. Телеметрия (`json_append`) экспортирует объёмы **в тиках** — контракт InfluxDB не разорван (для устройства Scale=0.1408 старые tick-значения мигрировали: 100→14, 1500→211, 2000→282 мл); после старта в логе есть `UnitsV2`-миграция строго один раз. Дата + средний расход последнего полива (строки «Текущий сеанс») персистятся (`P{Num}LastFloodTime`/`P{Num}LastFlowRate`, пишутся в `_record_flood()`) и переживают ребут; на свежеобновлённом устройстве до первого полива строки показываются как `nil` (ключи отсутствуют — ожидаемо).
8. «Нет воды» (flow limit): на `/svc` в OFF-состоянии поле «Лимит расхода» (мл/мин, значение из Store, «Применить») отрабатывает `?flowlimit=N`; после ребута значение пережито (Store), при 0 — детекция выключена; при включённой помпе с нулевым/низким расходом на главной через ≥5 с появляется баннер «Нет воды», в телеметрии `OutOfWater:true`; мусор/отрицательные значения отклоняются. Проверь, а потом верни значение 0 (или нужное), чтобы не менять поведение.

## Известные ограничения деплоя (проверено на железе 2026-10-06)

1. **`/ufsd?download=/<файл>` на отсутствующем файле не отвечает.** Прошивка 14.1.0.3
   держит соединение открытым и обрывает его вместо ответа 404 — измеренный факт:
   существующий `watering.be` скачивается за <1 с, отсутствующий `cfg.be` виснет до
   таймаута. Из-за этого `files_equal()` не мог завершиться ни разу для файла, которого
   на устройстве ещё нет, то есть **ровно для каждого модуля при первом многофайловом
   деплое**. `deploy.py` теперь трактует нечитаемую копию как «отличается» и идёт
   по пути заливки; читаемый файл по-прежнему верифицируется строго.

2. **`/svc` после `BrRestart` висел — ИСПРАВЛЕНО (2026-10-06).** Ограничение
   снято, ниже — как оно устроено, чтобы не вернулось.

   *Симптом:* после любого рестарта VM (`BrRestart`, т.е. после каждого деплоя)
   `/svc` не отвечал, причём **висел, а не отдавал 404**. `rc=0` деплоя при этом
   был зелёным.

   *Причина (по исходникам прошивки `14.1.0.3(6673fb9)`):* `FUNC_WEB_ADD_HANDLER`
   шлётся **один раз за жизнь VM** — ставится флаг `berry.web_add_handler_done`
   (`xdrv_52_9_berry.ino`). На `BrRestart` Тасмота посылает синтетический повтор
   на первом же тике `FUNC_LOOP`, то есть до того, как таймер фазы 2 (+4 с)
   выполнит `tasmota.add_driver(self)` в `init_sensors()` — драйверов в
   `tasmota._drivers` ещё нет, событие уходит «в пустоту» и флаг закрывается
   навсегда. Ниже на холодном старте была та же гонка: `Watering driver
   initialized 00:00:06.014` против `WIF: Connected 00:00:06.019` и
   `StartWebserver` из фазы `Every250mSeconds` — запас в доли секунды.

   *Почему висел, а не 404:* C-слот маршрута `/svc` оставался от прошлой VM, но
   `be_webserver_cb_deinit()` обнулил ему `vm`, и запрос к мёртвому callback'у
   прошивка молча не отвечает — соединение висит до таймаута (`/svc`: 0 байт за
   12 с при живой главной).

   *Фикс:* `init_sensors()` сам вызывает `self.web_add_handler()` сразу после
   `add_driver()` — тот же приём, что `start()` в референсном
   heating-controller: отложенный инит регистрирует маршруты сам, не дожидаясь
   одноразового события. Повтор безопасен по трём причинам: (1) `w_webserver_on`
   переиспользует слот по паре prefix+method, дублей не бывает; (2) если
   `Webserver` ещё не поднят, `WebServer_on` молча no-op (`if (Webserver ==
   nullptr) return`) и позже официальный ивент довершает — наш драйвер к тому
   моменту уже в `_drivers`; (3) реальных регистраций на VM выходит ровно одна,
   поэтому **гард идемпотентности не нужен и вреден**: он заблокировал бы именно
   холодно-стартовую ветку, где второй вызов — единственный результативный.

   *Приёмка:* `tests/cases/48_svc_route.be` (ровно один `/svc`, без дублей при
   повторном вызове) + `check_device.py` (`GET /svc` → 200, таймаут = провал).

3. **Проверка главной страницы в `deploy.py` слабее, чем кажется**: ищет `tr.sec` на
   статической `/`, а этот литерал есть в CSS-инжекте `web_add_main_button()` —
   проверка проходит даже при нуле отрендеренных секций. Строки каналов рендерятся
   не на `/`, а на XHR `/?m=1` (см. `BERRY_TASMOTA_CONTEXT.md`, механика главной
   страницы). Для ручной проверки: `curl 'http://<host>/?m=1'` и искать `Канал 1..N`.
