## ⛔ STRICT RULES (НЕ ИГНОРИРОВАТЬ)
1. **НЕТ внешних библиотек**: `import` разрешен только для встроенных модулей Tasmota: `string`, `json`, `math`, `path`, `persist`, `mqtt`, `gpio`, `webserver`, `sys`, `introspect`, `strict`, `undefined` и др. Никаких `requests`, `time`, `os` и т.д.
2. **НЕТ async/await или потоков**: Только callback-стиль и таймеры.
3. **НЕ блокируйте главный цикл**: `tasmota.delay()` блокирует весь Tasmota. Для задержек используйте `tasmota.set_timer()`.
4. **Ограничение памяти**: ~64 КБ на скрипт. Избегайте больших строк, вложенных структур и бесконечных массивов.
5. **Типы данных**: Berry динамически типизирован, но строго относится к `nil`. Всегда проверяйте `!= nil` перед использованием результатов I2C/HTTP/MQTT.
6. **Команды консоли**: Все кастомные команды ДОЛЖНЫ вызывать `tasmota.resp_cmnd_*()` для завершения.
7. **Неиспользуемый код**: Если проблема вызвана неиспользуемым (мёртвым) кодом — не удаляйте его без явного разрешения. Сначала спросите пользователя. Обращайте внимание на классы/функции, которые нигде не инстанцируются и не вызываются.

### `persist` module — ЛОВУШКИ (КЛЮЧЕВЫЕ ФАКТЫ)
1. **ПОЧТИ СИНГЛТОН, НО НЕ ВСЕГДА**: `import persist` в пределах одного скрипт-файла кэшируется → один экземпляр. **Разные скрипт-файлы (autoexec.be, watering.be, watering_ui.be) получают отдельные экземпляры** (внутри `persist.be` `init` возвращает новый `Persist()`). Все экземпляры читают/пишут один и тот же `_persist.json`, но синхронизации между ними НЕТ.
2. **`save()` перезаписывает файл ЦЕЛИКОМ** из памяти своего экземпляра. Данные, которых нет в этом экземпляре (например, записанные другим скриптом или вручную в файл), **будут затёрты**.
3. **Ручное редактирование `_persist.json` «на лету» НЕ надёжно**: работает только если скрипт перезагружен ПОСЛЕ правки и больше не вызывал `save()` из экземпляра, не знающего этих ключей.
4. **`save()` — запись во Flash, wear-out**: не вызывать часто (не в циклах, не каждый тик `every_second`). Сначала несколько `introspect.set(persist, k, v)` / `persist.key = v`, затем ОДИН `persist.save()`. В реальном `persist.be` `save()` пишет только если `_dirty` (после `setmember`) или передан `force_save=true` / вызван `persist.dirty()`.
5. **Рекомендация**: держать ОДИН `import persist` на верхнем уровне скрипта и использовать его во всех функциях (не импортировать повторно внутри функций).
6. **PersistStore (проект irrigation, многоканально)**: весь persist в `watering.be` идёт через класс `PersistStore` (`self.Store`, создаётся в `Watering.init()`; `register_channel('P{i}')` × 4, потом `load()` перед `init_sensors`). **Никаких глобальных ключей**: все ключи per-channel, префикс `P{Num}` (P1..P4) — реестр из 16 ключей на канал (`register_channel` вызывает `register(name, meta{default, policy, thr})`): `TargetDry`(800), `TargetWet`(760), `DryThreshold`(820), `SoakStartDose`(100), `SoakInterval`(7200с), `SoakTrendWindow`(86400с), `SoakDoseGrow`(1.2), `SoakDailyCap`(1500 тиков/24ч), `SoakMaxDose`(2000), `LastFloodVol`(0) + 6 ключей сессии (`SoilHPreFlood`, `SoilMaxHymidity`, `SoilMaxHymidityTime`, `PrevSoilMaxHymidity`, `PrevSoilHPreFlood`, `PrevFloodedVol` — default nil). Итого 4×16=64 зарегистрированных ключа (бюджет памяти см. gotcha #10). `Cache[name]` — актуальное значение, `Shadow[name]` — последнее записанное на Flash. **Запись отложенная**: `set()` сразу пишет значение в persist-мапу (в память) и помечает ключ в `Touched`, но `persist.save()` выполняется по политике: `immediate` (сразу), `debounced` (дефолт, 15s таймер `ID_PERSIST_SAVE` с пере-армом), `threshold` (относительный порог: `|value-shadow|/base >= thr`, `base = shadow`, при `shadow==0` → `base=value`, оба 0 → false). `flush(force)` пишет **только ключи из `Touched`** (нил-значения пропускаются) одним save и сбрасывает `Touched` — на Flash попадают только реально изменявшиеся ключи (дефолты не пишутся), а `load()` недостающие ключи покрывает дефолтом. `save_batch_entries(entries)` — батч из списка пар `[persist_key, value]` (ключ уже префиксован в источнике, см. `Plant._stats_batch()`), один save; старый `save_batch(names, source)` **удалён**. Калибровка Dry/Wet (`SoilSensor.SetDry/SetWet`) пишет `self.Prefix..'TargetDry'`/`'TargetWet'` через `Store.set` (debounced) — `SoilSensor` знает свой `Prefix`; если `Store == nil` (standalone) — прямой `introspect.set` + `save()`. В `init_sensors()`/`Plant.init()` ключи читаются через `self.Store.get(prefix..key)`, как **RAW-значения**; setter принимает **% влажности** (конвертация через `Hymidity2Raw()`).
7. **`auto_flood` / `every_second` (проект irrigation, многоканально)**: prev-статы и estimate-входы пишутся **на канал** (`Plant`) одной партией через `self.Store.save_batch_entries(self._stats_batch())` — список `[self.Prefix..key, value]` (5 ключей `P{Num}*` за один save: PrevSoilMaxHymidity, PrevSoilHPreFlood, PrevFloodedVol, SoilHPreFlood, LastFloodVol). **Только для пресета `normal`** (`_stats_enabled()`): сухой пресет (`WriteStats=false`) НЕ пишет Prev*/estimate-статы вовсе — save_batch в `start_session` и трекинг `SoilMaxHymidity` в `every_second` пропускаются. `every_second` (подтверждение SoilMaxHymidity) — `save_batch_entries(p.max_batch())` (2 ключа `P{Num}*`). `deinit()` — `Store.flush(true)` (форс сброса недописанного) + снятие таймера. Дамп: команда `Store` (JSON всех 64 ключей) + **веб-таблица только в detail-режиме** под аккордеоном «Канал 1» (ключи канала 1 с префиксом `Store.P1*`, см. ниже).
8. **Команда `counter1` (Tasmota)**: положительное число без знака (`counter1 500`) = PRESET (перезапись абсолютного значения); `counter1 0` = reset; `-n` = вычесть; `+n` = добавить. Форма `counter1??` (с `??`) — НЕ команда: это консольный суффикс группового применения, в справочнике команд не документирована. `_compensate_backflow()` использует preset-форму для коррекции счётчика после pump stop.
8. **Для тестов (stub persist)**: persist обязан быть **классом с виртуальными `member`/`setmember`** (`class Persist ... end; var persist = Persist()`), а не module-instance. Только так `introspect.set(persist, k, v)` реально попадает в внутренний map (module-instance не даёт virtual setters — `introspect.set` молча не пишет).

### 🔑 Web UI Тасmota 14 — МЕХАНИКА ГЛАВНОЙ СТРАНИЦЫ (обнаружена на практике)
1. **Главная страница — «оболочка»**: таблица сенсоров на `/` НЕ рендерится статически. JS-функция `la(argString)` делает асинхронный XHR `GET .?m=1&<args>` и заменяет содержимое `l1`. Хук `web_sensor()` запускается именно на этом `.?m=1`-запросе, а не на обычном `GET /`.
2. **`web_add_main_button()` рендерится в статическую часть `/`** — его видно сразу (кнопка Calibration, `<style>`-инжект с CSS-переменными, `<script>`-инжект); а строки `web_sensor()` появляются только после JS-«догрузки».
3. **Форма `<form method='get' action='/'>` с `m_`-инпутами НЕ доставляет аргументы в `web_sensor()`** — наблюдалось, что запрос без `m=1` не обрабатывается (значение не применялось). Рабочий способ — кнопка с `onclick='la("&m_key=value")'`: она дёргает `.?m=1&m_key=value`, и `web_sensor()` видит `webserver.has_arg("m_key")`.
4. **Паттерн для редактируемых полей**: инпуты с `id` + кнопка, собирающая строку из значений: `onclick='la("&m_soildry="+eb("soil_dry").value+"&m_soilwet="+eb("soil_wet").value)'`. Хелперы на странице: `eb(id)` = `document.getElementById`, `qs(sel)` = `querySelector`. **Per-channel настройки** (Soil Dry/Wet, Dry threshold, Soak start dose) — кнопка `⚙` (без текста, label `Настройки порогов`) в группе `Уставки` detail канала с `data-num/dry/wet/thr/dose` (текущие значения канала) → JS-попап `_wdSettingsOpen(this)` (в `document.body`, вне #l1, переживает поллинг) → сабмит шлёт **суффиксные** арги `m_soildry_N`/`m_soilwet_N`/`m_drythr_N`/`m_soakdose_N` (N=номер канала); bare-арги (`m_soildry` и т.д.) = канал 1 (legacy). Обработчики — цикл `for i: 1..NumChannels` в `web_sensor()`. **Поля попапа — одна JS-таблица `_wdF`** `[[inputId, label, argPrefix, dataAttr], …]`: один цикл генерирует HTML полей, копирует значения из `data-*` и собирает query-строку; добавить поле = строка в `_wdF` + блок-валидация в цикле `web_sensor()`. CSS и JS инжектируются как списки строк (один элемент = одно правило/фрагмент), склеиваемые один раз; палитра — CSS-переменные `:root` (`--wd-acc`/`--wd-green`/`--wd-bg-hdr`/...).
5. **Проверено**: `GET .?m=1&m_soildry=850` применяет порог (в логе `web_sensor: Soil Dry threshold set to 850`); `GET /?m_soildry=850` (без `m=1`) — нет.
6. **Прямой вызов `wp1.web_sensor()` из berry-консоли работает** и отдаёт полные строки; диспетчер `callBerryEventDispatcher` вызывает метод драйвера с 4 аргументами — в Berry это безвредно для методов без параметров.
7. **`Tasmota CSS` растягивает `input`/`button` на `width:100%`** (поля в столбик). Для одной строки — обёртка `<div style='display:flex;flex-wrap:wrap;gap:4px;align-items:center'>` + `style='width:auto'` на кнопке и `style='width:5em'` на инпутах.
8. **Паттерн «пер-вкладочное состояние web-UI» (без глобального флага в драйвере)**: Tasmota-страница хранит состояние НЕ в объекте драйвера, а в GET-параметре, который каждая вкладка шлёт сама. Реализация (см. `watering.be` `web_add_main_button()`/`web_sensor()`):
   - **Обёртка над `la()`**: инжектится `<script>` в статическую часть `/`; перехватывает `window.la` и добавляет `&me=<кодировка секций>` к каждому поллингу, если параметра ещё нет. Перехват работает и для рекурсивного авто-refresh `setTimeout(la, 2345)` — он вызывает `la` по имени, поэтому попадает в обёртку.
   - **Сервер рендерит пер-реквестно**: `var me = webserver.has_arg("me") ? webserver.arg("me") : ""` → `exp = string.find(me, "…") >= 0` — БЕЗ мутации `self.*`. Запрос без параметра → дефолт («последнего глобального состояния» не существует).
   - **`history.replaceState(null,'','?me=12c')`** зеркалит состояние в адресную строку → refresh сохраняет вид вкладки. Один параметр `me` вместо набора флагов: символы `1`..`9` = каналы soil1..soil9 (по числу `NumChannels`, см. Store-переменную `Channels`), `c` = Common.
   - **⚠️ В URL писать только свой параметр, БЕЗ `m=1`**: `m=1` в адресной строке при refresh отдаёт частичную сенсорную страницу (`.?m=1`-ответ без кнопок/оболочки). `m=1` нужен только внутри поллинга `la()` (`.?m=1&…`).
   - Каждая вкладка = свой JS-контекст (`window._wdSec`) → независимые поллинги и состояние. При разворачивании секций кнопка ▸/▾ не требует JS-флипа надписи: таблица перерисовывается каждым поллингом, сервер рендерит актуальную стрелку по текущему `me`.

### ⚡ Компактный/Detail-режим `web_sensor()` и кэш `_TimeStr()` (защита от LoadAvg)
1. **Проблема**: `web_sensor()` выполняется на КАЖДЫЙ `.?m=1`-запрос (при открытой странице — раз в секунду). Тяжёлые `string.format` (13 вызовов на сенсор) + `tasmota.strftime()` → заметный LoadAvg на ESP32 (~67/200 при открытой странице).
2. **Компактный по умолчанию**: `SoilSensor.web_sensor(expanded, sec, plant)`/`FlowSensor.web_sensor(expanded, sec)` — при `expanded=false` отдают 1 ряд за сенсор: soil → `Raw EMA(N)` + `Hymidity` (Raw и пороги скрыты), flow → только `Water used`. `Watering.web_sensor()` передаёт `expanded` **пер-реквестно** из одного параметра `me` (см. п.4). Все строки принадлежат секциям (always-эмитов больше нет): свёрнутая раскладка = заголовок-полоса секции на канал (имя + бейджи `raw`/`сухо`/`влажно` + статус-иконка, п.4b) + по 2 ряда на канал; «Dry soak»/«Dry threshold»/«Сеанс полива»/«Вода» ушли в detail (п.3), «FlowSensor Calibration mode» и кнопка сброса счётчика — в detail Common. **Секции эмитятся СЫРЫМ HTML** (`<tr class='sec'>`/`<tr class='sub'>`): `la()` переписывает только токены `{s}/{m}/{e}`, остальная разметка попадает в `#l1` как есть — это даёт CSS-классы, `title=`-тултипы, скругления полос (стили — `<style>`-инжект из `web_add_main_button()`, п.4c). Токены `{s}{m}{e}` у наших секций БОЛЬШЕ не используются.
3. **Detail-блок — пер-канальный, ОДНА логика для всех каналов, весь в одном методе `Watering.web_soil_detail(pi)`** (в т.ч. Уставки/Датчик/кнопка настроек; `SoilSensor.web_sensor` эмитит ТОЛЬКО заголовок-полосу): при развороте soil-секции `soil{i}` тело разбито на **группы** (`<tr class='grp'><td colspan='2'>Label</td></tr>` — подпись muted-uppercase + верхняя рамка как разделитель; внутри группы разделителей НЕТ): `Уставки` (Сухо, Влажно — **стек в 2 строки**: `800.00 raw` + `<span class='stk'>54.2% u</span>`, вторая строка = `Raw2Hu(RawDry/RawWet)`), `Датчик` (Raw, Raw EMA(N), Hymidity u, mV), `Сеанс` (Сеанс полива `active`|`wait` = `plants[i].AutofloodInProcess`, Вода `run`|`idle` = `plants[i].WaterIsOn()` (читает `tasmota.get_power` напрямую, без кэша); при `run` — живой расход `Rate*60` ml/min, `FlowSensor.Rate` обновляется каждую секунду, пока `RateMeasuring=true`), `Размачивание` (Dry soak — статус `none` или `soak, dose N` при активном dry-пресете; Dry threshold — уставка), `Текущий сеанс` (`SoilHymidity{Num} max`(+`max time`) и живые атрибуты `plants[i].LastFloodVol`, `plants[i].SoilHPreFlood`), `Предыдущий сеанс` (`PrevFloodedVol`, `PrevSoilHPreFlood`, `PrevSoilMaxHymidity` — читаются динамически через `introspect.get(plant, k)`), `Последний полив` (только если `plants[i].LastFloodTime != nil`: `Last flood time` = `plants[i].LastFloodTime`, `Last flow rate` = `plants[i].LastFlowRate` мл/мин — средний расход последнего полива канала, см. п.7). Значения `nil` выводятся как `nil`. **Исключены** только 2 ключа-дубля рядов сенсора: `TargetDry`, `TargetWet`. Detail-блок живёт под КАЖДЫМ развёрнутым каналом (свой `P{Num}`-префикс), а не только под soil1. Число каналов = `self.NumChannels` (Store-переменная `Channels`, default `'2'`, clamp 1..MAX_CHANNELS; команда `Channels [N]` — отчёт/установка, «restart required»; на `/svc` — поле `?channels=N` с той же семантикой + кнопка перезагрузки; при уменьшении параметры отключённых каналов из Store не удаляются). В свёрнутом виде эти ряды не выводятся вовсе. **Состояние полива/насоса в компакте — через статус-иконку в заголовке** (п.4b), а не отдельным рядом. В detail секции **Common** (`exp_flow=true`) дополнительно эмитится ряд `FlowSensor Calibration mode` и группа `Сброс` (ряд `Water counter` с кнопкой `Reset` — `<a class='wcbtn'>` акцентного цвета `#1fa3ec`, `onclick='if(confirm("Сбросить счётчик воды?")){la("&m_reset_water_counter_1=1");}return false;'` — нативный JS confirm; с главной страницы кнопка убрана, обработчик `m_reset_water_counter_1` тот же: при активной сессии `Counter1ResetPostpone=true`, иначе `FlowSensor.Reset()`). В detail КАЖДОГО канала в группе `Уставки` — ряд `Настройки порогов` с кнопкой `⚙` (без текста, `<a class='wcbtn'>`, `data-num/dry/wet/thr/dose` = номер канала + текущие RawDry/RawWet/DryThreshold/SoakStartDose) → `_wdSettingsOpen(this)` открывает JS-попап (см. п.4). **Все detail-строки без префикса `|`** (структура передаётся группами, а не отступами). Ряды и подписи групп собираются хелперами `wrow(label, value)`/`wgrp(label)` (глобальные функции, вывод байт-в-байт идентичен inline-разметке); onclick-атрибуты — хелперы `wonclick(js)` (атрибут в одинарных кавычках, JS внутри свободно использует двойные) и `wtoggle(sec)` (= `_secToggle("sec");return false;` для заголовка и шеврона); бейджи заголовка — `wpill(label, value)`. Показывается в detail канала в группе «Последний полив».

### `.bec` (Bytecode) — МЕХАНИКА ЗАГРУЗКИ (v13.4.0.3+)
1. **До v13.4.0.3** `load()` автоматически компилировал `.be` в байткод и **сохранял `.bec` рядом** (аналог `.py`/`.pyc`).

4. **Создать `.bec`** можно только явно: `tasmota.compile("x.be")` → `true` + создаёт `x.bec`.
5. **На практике (v14/v15)**: `.bec`-файлы в ФС не появляются при обычном `load()` из `autoexec.be` — это нормальное поведение, НЕ ошибка.

### 🐛 Berry GOTCHAS (обнаружены на практике)
1. `true`/`false` — **строчными буквами** (не `True`/`False`).
2. У `map` НЕТ `.has()` — проверять через `.find(k) != nil` (у list есть `.has()`).
3. `introspect.set(obj, k, v)` вызывает виртуальный `setmember` только у **class-instance**; module-instance — молча игнорирует (пишет/не пишет в память незаметно).
4. `string.find()` возвращает **индекс или -1** (нет `.has()`/`.contains()`); `string.split()` есть; `string.len`/`string.mid` отсутствуют — длина строки через `size(s)`, преобразование в строку через `str(x)` (не `string(x)` — у module `string` нет конструктора).
5. `list.push(...)` — добавление; `size(list)` — длина.
6. `try ... except .. as e, m ... end` — правильная защищенная конструкция. Синтаксис: **`..` (две точки)** ставится между `except` и `as`, т.е. `except .. as e` (перехват без переменной — краткая форма) или `except .. as e, m` (e — текст, m — стек-трейс). Без `..` нельзя писать `except e` — это `syntax_error` (`'e' undeclared`).
7. **ВАЖНО (Berry 1.1.0):** голый `except` (без `.. as var`) — НЕ гасит исключение. Тело `except` выполняется и print/log пишутся, но исключение всё равно пробрасывается выше: печатается `stack traceback`, `rc≠0`, дальнейший код не исполняется. Для реальной защиты используйте **только `except .. as e`** (или `.. as e, m`).
8. **Сборка для тестов — stock Berry v1.1.0** (не Tasmota-патч). Отличия, критичные для кода: (a) `introspect.setmodule` отсутствует — persist-стаб это файл-модуль `tests/modules/persist.be` (class-instance); (b) `string.format('%d', 'строка')` даёт **пусто**, а не число — для команды счётчика обязателен `%s` (`Reset()`, watering.be:253).
9. **`import string` — скоуп инструкции, НЕ глобальный**: `import string` внутри одной функции/метода доступен только там. Если вынесли код с `string.format()` в отдельный метод — добавьте `import string` в него (пример: `_compensate_backflow()` после рефакторинга из `rule_power`, watering.be:519). **ВАЖНО**: в тестовом окружении `string` доступен глобально (часть harness-стаба), поэтому на устройстве вылезает `syntax_error: 'string' undeclared (first use in this function)`, а тесты зелёные. Всегда проверять реальным `make deploy`.
10. **Memory-кварк stock Berry v1.1.0 (карты ~15-22 элементов)**: при создании нового `PersistStore()` ПОСЛЕ `deinit()` старого (reboot-флоу теста 26) запись в persist-карту может переехать на неправильный объект (use-after-free): значение ключа заменяется чужим (наблюдалось `LastFloodVol` 420 → '0'). Проявления недетерминированные. **Единственный рабочий обход (и он же — базовый механизм с итерации 2)**: `flush(force)` пишет только ключи из `Touched` — persist-мапа на ребуте остаётся МАЛЕНЬКОЙ (только реально изменённые ключи), даже при 64 зарегистрированных ключах (4 канала × 16). Тест 26 фиксирует это. **Бюджет памяти**: 64 ключа = 64 записи в `Meta`/`Cache`/`Shadow`/`Touched` + persist-мапа из фактически изменённых — вписывается в лимит скрипта (~64 КБ / инстанс-квоту); сверх 4 каналов не подниматься (`MAX_CHANNELS=4`).
11. **Баг Berry 1.1.0: цепочечный доступ `x.plants[0].member` в top-level коде теста**: после накопления мусора (много `list()`/map-аллокаций и persist-записей) выражение вида `wp1.plants[0].Prefix` (global → member-список → индекс → member) падает `index_error: list index out of range` при `<native>`-фрейме, хотя тот же доступ через локальную переменную (`var P1 = wp1.plants[0]; P1.Prefix`) работает. Внутри методов классов (`self.plants[0].X`) баг НЕ проявляется (тесты 13/18/19/35-40 это нагружают). **Правило для тестов**: в top-level коде НЕ писать трёхуровневые цепочки `wp1.plants[0].X` — выносить в локальный алиас (`var P1 = wp1.plants[0]` в начале, после `wp1 = Watering()` переобъявлять `P1 = wp1.plants[0]`). Паттерны `wp1.Store.method(...)` и `wp1.SoilSensors[0].Update(...)` безопасны (проверено тестами).

## 📐 SoilSensor & EMA (проект irrigation) — ТЕКУЩЕЕ СОСТОЯНИЕ
- **`watering_ui.be` — рудимент**: незавершённая попытка вынести web-интерфейс в отдельный модуль. Не используется, в пуш/поддержку не входит, не развивать.
- **Все актуальные расчёты идут в RAW отсчётах ADC** (сырые `Raw`/`RawEma`; пороги `RawDry`/`RawWet`). Калибровки в % (`Hymidity`) и мВ (`mV`/`Hu`) — **недоделаны, не трогать**.
- **Пороги**: `RawDry=800`, `RawWet=750`; линейная шкала по двум точкам `setScale(842, 1105)`.
- **Пороги редактируются** (RAW, не %): команды `SoilDry`/`SoilWet` (persist `TargetDry`/`TargetWet` через `Store.set`, debounced 15s) и веб-попап канала (кнопка `⚙` в группе `Уставки` detail, суффиксные арги `m_soildry_N`/`m_soilwet_N`; bare `m_soildry`/`m_soilwet` = канал 1, legacy). **Валидация**: разрыв `|RawDry - RawWet|` должен быть **строго > 20**, иначе значение не применяется (отвергается). Реализация: `SoilSensor.SetDry(raw)`/`SetWet(raw)` возвращают `bool`.
- **Сухая замочка — конфиг**: порог `DryThreshold` (RAW, дефолт 820) и стартовая доза `SoakStartDose` (дефолт 100) редактируются командой-пулом `DrySoak` (веб-попап канала: `m_drythr_N`/`m_soakdose_N`; bare `m_drythr`/`m_soakdose` = канал 1, legacy) через `Store.set` (debounced). Команда `DrySoak` с пустым payload — статус (`preset=`, `DryThreshold=`, `dose=`, `since=`), со `start` — принудительный запуск dry-замочки (ставит пресет `dry` и доза `SoakStartDose`), иначе — `resp_cmnd_error()`. `init_sensors()` восстанавливает `DryThreshold` из Store; `deinit()` снимает команду.
- **EMA** (`EMAN=600`): `k=2/(N+1)`, `RawEma_new = RawEma_old*(1-k) + Raw*k`; инициализация `RawEma = Raw` при первом тике. Функция `EMA()` в начале watering.be.
- **Наблюдаемый артефакт (приемлемый)**: в InfluxDB кривая EMA огибает кривую RAW СВЕРХУ со смещением +1..+2. Возможные причины: округления, дискретность отчётов (раз в 5 мин попадает на заниженное значение), помехи питания. **Пользователя смещение устраивает — не оптимизировать, не «чинить».**
- ADC: `Raw2mVScale` из делителя 30k/30k (≈1.197 mV/source), полином `Hu_C` — недоделка.

### 🔄 FSM автополива (event-driven, многоканально) — КРАТКОЕ РЕЗЮМЕ
- **Архитектура (итерация 2)**: `Watering` = диспетчер + общие ресурсы (4 `SoilSensor` A1..A4, общие `FlowSensor` C1/C2, общий `PersistStore`), `Plant` = канал (свой насос `Power{Num}`, свой `SoilSensor`, своя FSM, свои persist-ключи `P{Num}_*`). `MAX_CHANNELS = 4`. Единица арбитража — **одна заливка + кап времени** (`MaxPumpRun=60` → `PulseTime{Num}`): реле включаются строго по одному.
- **Маршрутизация**: `POWER{Num}#State` → `Watering.rule_power` → `PowerMap['POWER{Num}']` → `Plant.rule_power` → `water_on/water_off`; BUTTON1 → `rule_button1` → `request_manual(plants[0])`. Кроны: `auto_flood` (окно 14–01), команды `autoflood`/`SoilDry`/`SoilWet`/`DrySoak`/`Store` — канал 1 (первичная зона). `_flooding_plant()` = канал с `WaterIsOn()` (shared C1 → сериализация).
- **Очереди нет**: `Plant.due()` = `SoilSensor.IsDry() && !AutofloodInProcess` (производное, пересчитывается на каждом sweep). Sweep (`auto_flood()`): пропускается, если `_flooding_plant() != nil`; иначе round-robin (`_rr_idx`, от нуля), стартует ОДИН due-канал через `start_session()`. Sweep-события: cron + истечение cooldown-таймера канала. **Отклонение**: sweep при завершении заливки НЕ добавляется (сломал бы test 12/29 — `start_session` зануляет `LastFloodVol`), cooldown обрабатывается per-plant через `request_repeat`.
- **`request_repeat(plant)`**: если `_flooding_plant() != nil` (чужое реле ON) → пере-арм soil-таймера канала с retry 60с (`_rearm_soil_check(60000)`); иначе `plant.start_flood()`. `request_manual(plant)` — с тем же guardian (кнопка/`DrySoak start`). Это и есть сериализация общего счётчика C1.
- **Пресеты (FloodPreset, per-plant)**: на каждый заход выбирается стратегия — `normal` (классика: эскалация дозы ×1.2 на интервале 2ч/24ч, пишет Prev*/estimate-статы) или `dry` (сухая замочка: малые фикс-дозы на каденсе `SoakInterval` 2ч, адаптация по тренду `SoakTrendWindow` 24ч, DailyCap, НЕ пишет статы). Выбор в `Plant._pick_preset()`: `RawEma > DryThreshold` (persist `P{Num}DryThreshold`, дефолт 820) → `dry`, иначе → `normal`. Все параметры пресета читаются по префиксу канала (`FloodPreset(type, store, prefix)`). При `dry` `DrySoakDose = SoakStartDose` (100), `DrySoakStartMillis = now`. Объект пресета живёт в `Plant.Preset`, снимается в `_autoflood_end()`/`_drysoak_end()`. `_pick_preset()` вызывается в `start_session()` ДО проверки `_stats_enabled()` (порядок классического auto_flood): dry-сессия не должна писать Prev*/статы.
- **Сухой evaluate (`FloodPreset._evaluate_trend`)**: 1) `RawEma < StopRaw`(=DryThreshold) → stop, `_drysoak_end()` (сессия закрыта, Prev* не тронуты); 2) текущий RawEma в кольцо `DryEmaHistory` (prune до `SoakTrendWindow`); 3) DailyCap: сумма тиков в `DryDailyTicks` за 24ч `>= SoakDailyCap` (1500) → pause + пере-арм таймера; 4) окно тренда не заполнено → repeat той же дозой; 5) окно заполнено: `delta = RawEma_now − RawEma_старт_окна`; `delta >= 0` (нет отклика) → `DrySoakDose ×= SoakDoseGrow` (кап `SoakMaxDose` 2000), repeat; `delta < 0` (влажность растёт) → hold + пере-арм таймера. Результат evaluate → `timer_soil_transition_after_flooded` → при 'repeat' → `Owner.request_repeat(self)` (арбитраж).
- **Планировщик**: `auto_flood()` (cron, часы 14–01) — sweep round-robin; при выборе due-канала → `Plant.start_session()`: 1) `_pick_preset()`; 2) при `_stats_enabled()` (только `normal`) копирует Prev*-статистику + estimate-входы и сохраняет одной партией (`Store.save_batch_entries(self._stats_batch())`, один save); 3) `LastFloodVol=0`, `AutofloodInProcess=true`, `SoilHPreFlood=RawEma`, сброс Max/Time (и Temp); 4) `start_flood()`.
- **`start_flood()`** — единая точка запуска полива (сессия, повтор, кнопка). Если `Preset == nil` — `_pick_preset()`. Дry-check: `RawEma <= RawWet` → лог `"soil not dry (RawEma<=RawWet), skip"` (помпа НЕ включается); иначе `PlannedFlood = Preset.dose(self)` (для `normal` = `planned_dose()` — `estimateflood()` при валидной оценке, иначе `Counter1FloodDefault`; для `dry` = `DrySoakDose`) и `Power{Num} 1`. Кнопка и повтор НЕ делают init-сессии (`AutofloodInProcess` выставляется только `start_session`).
- **Проверка результата** (`Plant.timer_soil_transition_after_flooded`, таймер `ID_SOILTRANSITION_AFTERFLOOD_P{Num}`, через 2ч): диспетчер — при `Preset != nil` → `Preset.evaluate(self)`, иначе → `_escalate_evaluate()`. Классика: земля всё ещё сухая → `Counter1FloodDefault × 1.2` (cap `MaxFlood`) и 'repeat' → `request_repeat`; влажно → `_autoflood_end()` (сессия закрыта). **Кап сеанса**: в `_record_flood` при normal и `LastFloodVol > MaxFlood` сессия закрывается сразу (`remove_timer` + `_autoflood_end`) — защита от перелива при затяжном (калибровочном) сеансе; следующий день планировщик начнёт свежий сеанс.
- **`estimateflood()`** (per-plant) строит оценку на **Последней завершённой сессии — Prev*** (`PrevSoilHPreFlood − PrevSoilMaxHymidity`, `PrevFloodedVol`), которые копируются в start_session ДО обнуления текущих полей и персистятся там же — оценка работает и после ребута.
- **Старт** (`Plant.water_on()`): защита от запуска на мокрой почве (`IsWet()` → `Power{Num} 0`), TelePeriod 10, `FinishRule = COUNTER#C1 >= before+backflow+доза` (общий счётчик!), `RateMeasuring=true`.
- **Лимит** (`rule_flooded`): превышен счётчик → `Power{Num} 0`; аппаратный кап времени — `PulseTime{Num}` из `MaxPumpRun`.
- **Стоп** (`water_off()`): читает Counter1 из сенсоров, `_compensate_backflow(Counter1)` — вычитает backflow из счётчика (preset `counter1`) и из дельты; `_record_flood(CounterDelta)` — `LastFloodVol += delta`, при `Preset.Type == 'dry'` дополнительно пушит `{ms, ticks}` в `DryDailyTicks` (для DailyCap), задержка проверки 2ч (dry: SoakInterval); при normal и `LastFloodVol > MaxFlood` — сессия закрывается капом объёма (таймер проверки не ставится) + таймер `ID_SOILTRANSITION_AFTERFLOOD_P{Num}`; при `CounterDelta==0` вместо него `_end_session_no_water()`. Затем таймер возврата TelePeriod 300 через 60с.
- **Завершение** (`_autoflood_end`): сброс флагов, опциональный отложенный сброс счётчика (`Counter1ResetPostpone`), `PauseSoilMaxStat=false`, `Preset=nil`.
- **Фон** (`every_second`, 1/с): `read_sensors` → Update сенсоров; трекинг минимума влажности по каждому каналу (кроме периода `PauseSoilMaxStat` И пресета `dry` — `_stats_enabled()`): текущий минимум живёт в `SoilMaxHymidityTemp`/`SoilMaxHymidityTimeTemp` (в память, не персистятся); подтверждение после роста `RawEma > Temp+5` при новом минимуме (`SoilMaxHymidity==nil || Temp < SoilMaxHymidity`) → `SoilMaxHymidity=Temp`, `SoilMaxHymidityTime=TimeTemp` и `Store.save_batch_entries(p.max_batch())` (один save). `SoilMaxHymidity != nil` = подтверждено; после ребута в persist лежит **последний подтверждённый** минимум — `LastSoilMaxHymidity` в телеметрии эмитится сразу после загрузки (без нового +5-подтверждения). **Инвалидация устаревшего пика**: при тех же условиях `!PauseSoilMaxStat && _stats_enabled()`, если `RawEma < SoilMaxHymidity` (почва стала влажнее последнего подтверждённого минимума, т.е. сохранённый пик завышает влажность) — `SoilMaxHymidity` и `SoilMaxHymidityTime` обнуляются (in-memory; persist-поле не трогается); ниже будет подтверждён новый (более низкий) минимум обычным путём +5. Окно впитывания после полива (`PauseSoilMaxStat=true`) и сухая замочка (`dry`, `_stats_enabled()=false`) пик НЕ инвалидизируют.
